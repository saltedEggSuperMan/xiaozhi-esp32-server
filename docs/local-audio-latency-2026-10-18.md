# 2026-10-18 本地语音响应延迟排查

结论：延迟来自多个环节叠加。当前最明确的等待是 700 ms 静音判定、云端 Edge TTS 完整片段合成，以及每轮重新打开 PC 声卡。LLM 首段文字在近期普通对话里约 0～1 秒，个别 TTS 请求的 429 与重试会进一步拉长等待。

本次仅做配置读取、日志分析和诊断测试；没有修改业务配置、播放实现或重启服务。TTS 测试使用两条固定测试文字，结果留在内存，没有播放；声卡测试只写入静音。未打印密钥或用户对话内容。

## 当前有效配置

- 播放出口：`server_pc`，设备为系统默认输出，软件音量 0.6。
- VAD：Silero，`min_silence_duration_ms: 700`，threshold 0.5。这里读取的是运行部署对应的管理 API 配置；不能用仓库 config.yaml 里的 200 ms 代替这个实际值。
- ASR：本地 FunASR/SenseVoice（`fun_local`）。
- LLM：`deepseek-flash`；Intent 为 `function_call`，此路径没有再调用一遍独立的意图识别 LLM。
- TTS：Edge。
- 短期记忆查询直接返回内存字符串，不发起另一个云端请求。

## 已经观察到的对话耗时

最近 9 轮具有完整“识别文本 → LLM → 首段文字 → PC 音频入队”日志的对话，识别完成到 PC 入队为 1～5 秒，中位数 2 秒，普通样本主要为 1～3 秒。以下是其中部分样本：

| 识别完成时间 | LLM 开始到首段文字 | 首段文字到 PC 音频入队 | 识别完成到 PC 入队 |
| --- | ---: | ---: | ---: |
| 20:10:42 | 1 秒 | 4 秒 | 5 秒 |
| 20:16:11 | 1 秒 | 2 秒 | 3 秒 |
| 20:17:35 | 1 秒 | 1 秒 | 2 秒 |
| 20:18:18 | 1 秒 | 2 秒 | 3 秒 |
| 20:22:22 | 1 秒 | 1 秒 | 2 秒 |

20:10:46、20:17:59、20:18:00 等处记录了 Edge TTS HTTP 429 失败及重试。第一例因此延后到 20:10:47 才开始向 PC 交付音频。

限制：这些历史日志只有秒级精度，数值是粗略阶段差。`发送第一段语音` 在源码中是 FIRST 文字消息，发生在 TTS 真正产出音频之前；`音频输出: server_pc` 是创建播放队列，也不是物理声波已经发出。以上时间还不包含说话结束后的静音判定、ASR 推理及声卡缓冲，不能直接当作“说完到听见”的总延迟。

## 独立计时结果

使用实际部署的 Edge 音色及速率参数、同一服务端代码里的端点配置，仅做两次测试，没有进行高频压测：

| 测试文字长度 | 收到第一个云端音频块 | 收到整个音频片段 | MP3 转换到首个 Opus 包 |
| --- | ---: | ---: | ---: |
| 8 字符 | 969 ms | 1256 ms | 44 ms |
| 32 字符 | 770 ms | 1078 ms | 45 ms |

当前 Edge `text_to_speak()` 先把整个片段收集到 bytearray；基础类等待它返回，再解码并编码成 Opus。虽然方法名是 `to_tts_stream`，这条 Edge 路径在云端第一块到达时还没有开始播放。本次样本中，等待片段收完额外增加约 288～308 ms；云端连接和首块等待本身仍约 0.8～1.0 秒。

声卡静音测试：

| 输出接口 | 打开声卡 | 首次 20 ms 数据写入 | 驱动报告缓冲延迟 |
| --- | ---: | ---: | ---: |
| 系统默认（MME） | 163、258、940 ms | 42～44 ms | 100 ms |
| 指定 Realtek 扬声器 WASAPI | 176、180 ms | 0～0.1 ms | 40 ms |

声卡启动波动较大，不能用三次测试推断固定收益。现有 PCSpeaker 每个回答轮次创建一次线程和输出流，因此每轮都会支付打开设备的成本。WASAPI 样本缓冲更小，但仍有约 0.18 秒的打开成本。上述声卡写入和驱动报告数字也不能简单相加当作实际听觉延迟。

本机管理 API 获取设备配置本次约 33 ms；一般在建立连接时读取，不是普通同一连接每轮回复的主要等待。

## 实施结果

后续已将本机静音等待设为 400 ms，并实现同一连接复用 PC 声卡，增加 ASR 毫秒级计时。Windows Huihui 本地合成实测更快，用户也确认响应明显加快，但试听自然度不满意，最终选择切回 Edge 并保留上述优化。Edge 增量解码尚未实施。此前的阶段测量描述的是优化前的状态，详细测试与切换方法见 [Windows 本地语音合成与响应优化](windows-local-tts.md)。

## 优化顺序

1. 先在实际管理配置把静音等待从 700 ms 试调为 400～450 ms，理论上可少等约 250～300 ms；需要用完整句子验证是否更容易在说话停顿处误截断。只改 config.yaml 无法覆盖此完整部署的实际 VAD 配置。
2. 复用 PC 输出流，在打断时清空本轮缓存，在断线/退出时释放声卡，避免每轮重新开设备。可比较固定 WASAPI 与系统默认输出的实机效果，同时保留设备模式。
3. Edge 改为真正的增量解码播放，收到可解码的 MP3 数据就开始产出 PCM/Opus；本次样本对应的可消除等待约 0.3 秒。必须验证流式解码边界、尾音、打断及错误重试，不能把每个 MP3 网络块当成独立文件直接解码。
4. 优化过短 TTS 分段和 429 处理，减少连续独立请求及重复重试。稳定性改善与首次响应速度需分别评估。
5. 增加不带对话内容的毫秒级分段计时，再决定是否更换 ASR 或模型。当前 INFO 日志没有保留 ASR 的推理耗时，也没有麦克风端最后一个真实语音采样时刻；本次不能精确归因这个环节。
